## 1. Code implemented in this first iteration

1. **Tokenizer-bounded structural chunking:** `TextChunkingService._preferred_boundary` now prefers the start of a complete Markdown `#` through `######` heading when it falls in the latter half of a fitting chunk. This keeps a heading with its following section when possible. It still falls back to paragraph/newline/sentence/word boundaries, uses exact tokenizer count and rejects oversized input without dropping/reordering normalized characters. It does **not** promise topic-boundary detection in PDF/DOCX plain text.
2. **Validated decoder repetition control:** `Mt5ModelProvider` supports integer `model.no_repeat_ngram_size` in **[0, 6]**; zero is compatible with the Stage 9 decoding behavior. The option is passed to the pinned Hugging Face `generate` call; model lifecycle, resource ceilings, concurrency and DI are unchanged.
3. **Configuration separated by environment:** `appsettings.development.yaml` enables trial `no_repeat_ngram_size: 3`. The production `appsettings.yaml` explicitly keeps `0` so **production decoding** remains the Stage 9 default. The section-boundary heuristic is shared by both environments; it is lossless but can change chunk grouping. The development config can be rolled back by changing `3` to `0` (without touching weights or deleting files).
4. **Auditable experiment:** `quality_benchmark run` now records `no_repeat_ngram_size` in the generation metadata. A new `benchmarks.stage10_compare` CLI compares fixed input cases/tier pairs, output lengths, n-gram repetition, elapsed times, token counts and generation configurations. It refuses mismatched dataset digests or case/length sets. It never copies raw summary text or unknown metadata into its comparison report and **never claims semantic improvement without human reviews**.

This is one **joint candidate** (chunk boundaries + decoder n-gram setting), not a causal experiment isolating every knob. Further ablation of `num_beams`, `length_penalty` and `repetition_penalty`, map/reduce preservation and human annotation are future iterations **within Stage 10**. Changing all three decoder parameters at once would confound comparisons.

### Candidate v2 — controlled, offline Map evidence ablation

Unrepresentable candidates are skipped; no raw input or generated text is logged in the API.

**Risks and limitations:** this is an extractive heuristic, not semantic evidence ranking. It favors bullet-heavy Markdown (the available failure case) and may miss facts expressed in ordinary prose, sentence fragments, pages or tables. Model output may still drop preserved clauses during subsequent Map/Reduce passes. Appended excerpts can increase hierarchy depth, token work and CPU latency. Output claims cannot be marked `covered` until independently reviewed. The `preserve_map_evidence` option is **not exposed over HTTP**. This is a **single-variable ablation relative to the already evaluated Candidate v1**: n-gram=3, model revision and section-aware chunking remain fixed, with only Map evidence preservation changed.

### Candidate v3 — controlled, source-grounded final fallback (disabled by default)

To test whether **final-generation omission** can be mitigated without prompt hacking, checkpoint changes or fabricated source facts, the long-text service now accepts a **second experimental keyword** `source_grounded_final=True`, **only alongside** `preserve_map_evidence=True`. Normal API calls keep both flags **False**.

On multi-chunk text only, the optional path records the exact **original-source sentences actually carried forward in first-level Map results**. It still performs the same final mT5 Reduce call, validates its output normally, then constructs a *source-only* extractive alternative in **source order**, adding whole clauses only if the actual tokenizer count stays within the final tier's encoded-token ceiling (medium=80). The extractive candidate **replaces** the generic final Reduce output only when at least one clause fits; otherwise the original generated result is returned. Source excerpts are never paraphrased, truncated or injected from benchmark labels. Subsequent Map levels cannot contribute unverified/generated text to this fallback.

**Tradeoffs:** this is explicitly **extractive, not abstractive**, and prioritizing early source clauses can bias coverage away from later sections or different viewpoints. It may be a set of disconnected sentences rather than coherent prose; original source sentences may themselves contain disputed claims. It does not guarantee coverage, faithfulness, fairness or readability. It is a *single-variable candidate* relative to v2: same pinned model/decoder/chunking and Map source-excerpt trial, plus the final replacement policy. The existing API and Production are unchanged.

The benchmark CLI records `pipeline_settings.source_grounded_final`, prohibits the trial on any `holdout` or `all` split, and the paired comparator surfaces both baseline/candidate flags. The output file may include **verbatim source content**: store it locally, check before sharing, never commit it.
